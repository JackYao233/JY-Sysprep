从样本出发，核对 VIP 免广告、主页修改与下载执行之间的关系。

调查日期：2026-10-22 · 最后修改：2026-11-21（补充复核） · 状态：静态分析完成，未进行运行验证

研究整理：Codex · 补充复核：Claude

我们本次研究的 x64 样本中，存在浏览器主页修改及下载、运行外部文件的流程，并与 VIP 免广告状态联动。从还原代码可以追踪到“默认开启标志 → 写入封装配置 → 部署时读取 → 进入主页修改和下载执行流程”的调用链。

由于本次采用离线静态分析，没有访问下载服务器，也没有运行目标程序，因此尚不清楚实际会下载哪些文件、安装哪些软件。代码同时包含“VIP 免广告”菜单，认证成功后会关闭相关标志；实际效果仍需在隔离环境中验证。

2026-11-21 补充复核：在程序内部，关闭推广的唯一途径是 VIP 认证；程序内的许可协议没有提到这些行为。推广在用封装出来的系统部署的每台电脑上运行，下载的文件安排在部署后首次登录时运行，且不做任何校验。详见 08 与 09。

本页结论只针对下面列出的样本与静态代码，不等于对所有历史版本、当前在线服务或所有运行环境的判断，也不是“杀毒实测报告”。

02 · 怎样分析，怎样保留证据

  1. 只读检查原件。登记文件大小、SHA256、版本信息与签名，保持研究样本原样。
  2. 离线提取脚本。识别到 AutoIt 的 SCRIPT 资源与 EA06 标记，使用 AutoIt-Ripper 提取两份脚本，以 .au3.txt 保存，避免作为脚本误运行。
  3. 只还原数据，不执行目标脚本。解析函数索引表与字符串表；在临时内存中使用系统 CryptoAPI 解码资源。没有解释执行 AutoIt 的 Execute 表达式，也没有启动目标程序。
  4. 核对数据完整性。x64 主字符串表的三个解码块均通过脚本内置 SHA1 的一致性检查；恢复出 7,163 个字符串／数值项，以及 1,743 个函数表项。函数与数值替换后的文本保留原提取脚本的行号。
  5. 追到实际分支。从菜单、配置保存和部署入口向下追踪，而非仅凭“VIP”或“2345”字符串下结论。

解码过程中只使用临时加密上下文，没有创建持久密钥容器。目标程序、提取出的脚本与生成的批处理均未运行；没有请求推广服务器或下载其下发文件。

03 · VIP 与推广标志，确实连在一起

某封装软件在简介中写明：

专业版具备标准版全部功能，0 广告、0 推广，需 VIP 权限下载使用。

那么，广告和推广是如何与 VIP 状态关联的？我们从样本代码中追踪了相关流程。

静态代码已确认

标志默认开启，VIP 认证成功后关闭

函数 OGEOPWVWSRRVXDF 保存一个初始值为 1 的状态。普通读取返回当前状态，传入参数时更新状态。两处配置收集逻辑把该状态写入 SSP 字段。

静态状态：$DFABDH = 1
配置保存：$AEIIFX["SSP"] = OGEOPWVWSRRVXDF()
VIP 成功分支：OGEOPWVWSRRVXDF(0)

对应位置：x64 还原脚本第 31636–31643 行；第 7016、16416 行；第 6729–6747 行。上面是保留标识符、简化排版后的摘录。

菜单定义中存在 “VIP 免广告”。菜单事件进入认证函数；认证成功会显示 “VIP 认证完成”，并在成功状态分支关闭该标志。界面提示也明确写有 “登录 VIP 完成认证后，可开启更多功能或免广告”。

对应位置：第 11045–11046、27533、27875、30920 行。

这份样本实现了“VIP 认证与免广告状态联动”。但仅凭本次离线分析，甚至不能确保购买 VIP 后系统的纯净性。

补充复核 · 静态代码已确认

程序内只有一个关闭点

补充复核穷举了标志函数在全文的全部引用，一共四处：第 6745 行的 OGEOPWVWSRRVXDF(0)，只在 VIP 已认证时执行；第 7016、16416 行把当前值存入 SSP；第 18166 行是混淆器生成的函数登记表，同一段里每个函数都这样登记，不是调用。

SSP 字段在全文只有这两处写入和部署时的一处读取（第 26401 行）。界面上没有对应的复选框，封装配置里没有对应的设置项，也没有命令行参数会改变它。因此在程序内部，关闭推广只有 VIP 认证一条路。程序之外的渠道和运行时数据，静态分析无法排除。

对应位置：第 6729–6747、11011、11046、18166、26401 行。

补充复核 · 推断

推广与否在封装那一刻决定

部署时读取的是封装时保存的配置（第 20836–20841 行），部署阶段不再检查 VIP 状态。是否推广由封装者在封装那一刻的 VIP 状态决定，并固化在镜像里。VIP 是限时的，到期提示写着到期后“将无法使用 VIP 权限”（第 19236–19246 行）。由此推断：VIP 到期后再封装的镜像会重新带上推广，到期前封装的镜像不受影响。这一点没有经过验证。

04 · 主页修改，不只是网址字符串

静态代码已确认

部署分支会调用 Edge 配置修改逻辑

部署函数 GSOWTITXQQRLSFI 调用推广检查函数 XPAWHQZSWVFQKEN。后者检查配置中的 Other → SSP 或 Sysprep → SSP；任一为真时才继续。随后调用的包装函数传入版本标识 [版本标识]。

  1. 读取封装配置中的 SSP
  2. 拼接推广地址与 版本标识
  3. 进入主页配置修改函数

调用链：第 27580–27586 行 → 第 26400–26404 行 → 第 21567–21570 行 → 第 8175–8199 行。

主页处理函数会构造 homepage、session.restore_on_startup = 4、startup_urls，写入 Edge 的 initial_preferences。代码还包含清理 Secure Preferences、First Run 等文件，以及删除 Edge\PrefsLightweight 注册表项的操作；在识别到相关正在使用的浏览器配置时，存在关闭 msedge.exe 进程的分支。

$HWHOAL["homepage"] = $SPBLSC
$HWHOAL["session"]["restore_on_startup"] = 4
$HWHOAL["session"]["startup_urls"] = …
目标文件：…\initial_preferences

对应位置：第 19424–19434 行的入口，以及第 13631 行开始的 QZCAPOPUBMUYTIY 函数。省略部分为原脚本中的辅助函数调用。

文件中确有导航地址映射。但这条部署调用链显式传入的地址由推广域名与版本标识拼接形成，不能把默认映射与实际调用参数混为一谈。本文不展示具体域名。

映射：第 11058–11074 行。域名：第 31730 行起的 VDKJIZEGTCTNYND 函数，具体域名已匿名；版本标识：第 27541 行起。

确认的是“代码具有并调用了这些操作”，不是已经在本次测试中观察到用户主页被改。不同 Edge 版本、权限、文件状态与配置，都可能影响实际结果。

补充复核 主页函数全文只有一个调用点（第 8183 行），总会传入“推广域名 + 版本标识”。导航地址映射里的两个导航站地址只是该函数不传参数时的默认值，在这条链上用不到。两个地址都带查询参数，看起来像推广渠道号，这一点是推测。

05 · 下载、运行、后续启动与清理

静态代码已确认

生成隐藏执行链，并准备三个下载项

同一推广入口会设置下载地址为 [推广域名]/d/[版本标识]。下载项列表初始化为 1 2 3，生成的批处理逐项请求对应地址，按服务器返回的文件名查找下载结果，再启动文件。

安装准备函数会建立 SoftInst 目录，将其设置为隐藏属性，在其下创建“时间戳＋随机字符”的子目录，释放 wget.exe，并生成 inst.cmd 与用于隐藏启动的 inst.vbs。

本部署调用传入的标志为 11（1 + 2 + 8），未设置直接启动分支所检查的 4 位。在这条调用链中，流程会按环境条件安排 RunOnce 后续执行；不能据此写成“调用到这里就立即下载安装”。

离线分析能够确认代码中存在下载、运行外部文件的流程。由于没有访问下载服务器或运行样本，我们尚不清楚实际会下载什么文件、安装哪些软件，也没有验证这些文件的安全性及安装结果。

补充复核 · 静态代码已确认

正常部署时，安排在部署后首次登录运行

标志 11 的三个分支最终都会写入 RunOnce：目标系统离线时写离线 hive（1 位）；以 SYSTEM 运行且 @HomeDrive 为空时写 HKLM\…\RunOnce（2 位，部署阶段正属于这种情况，判断函数在第 28700 行）；普通运行时 4 位未设、8 位同样写 RunOnce。推广所在的“部署中”阶段会无条件写入部署运行列表（第 9171–9174 行）。因此在正常部署路径上，下载和运行发生在部署完成后第一个用户首次登录时，RunOnce 值名为 SoftInst。

对应位置：第 11929–11957、28700–28703、9171–9174、20860–20862 行。

补充复核 · 静态代码已确认

下载的文件不做校验，也没有前置条件

  • 不校验：批处理用 --trust-server-names 让服务器决定文件名，下载成功即运行，全程没有哈希或签名检查。服务器下发什么，部署出去的电脑就运行什么。不论意图如何，这本身就是安全风险：服务器或域名一旦出问题，所有部署出去的电脑都会受影响。
  • 没有前置条件：推广主函数开头只检查是否为编译后的程序（@Compiled，第 756 行）和推广地址是否以 http(s) 开头（第 14436 行），不检查联网、地区、语言、虚拟机或日期。没有网络时下载失败，批处理随后自行清理。
  • 隐藏的只是外壳：窗口隐藏的是 vbs 和 cmd 这一层。下载下来的程序以 start /B 正常启动，用户能否看到它的界面，取决于服务器下发的是什么文件。

对应位置：第 31576–31635、8175–8182、756、14436 行。

07 · 还缺什么证据

  • 界面告知与取消方式：补充复核已核对程序内的许可协议，其中没有提到这些行为，程序内也没有取消开关（见 03、08）。仍需确认官网、下载页等程序外渠道是否另有说明，并录制同一版本从启动到封装确认的完整过程。
  • 实际行为：需要从干净快照比较封装前后与首次登录后的主页设置、进程、文件和注册表变化。
  • 服务器下发：需要记录实际响应、下载文件的哈希与签名，再判断具体软件。只出现 2345／360 字符串并不够。
  • 普通与 VIP 对照：需要合法有效的两种状态在相同环境、相同配置下对比，而不是修改认证程序或绕过验证。
  • x86 对照：补充复核在 x86 脚本中找到一个与推广标志函数结构完全相同的函数，全文仅此一个，提示机制相同；但调用经过加密表间接跳转，尚未解码，调用链仍未确认。

本次没有进行上述运行测试。原件未修改，调查也没有改变任何 VIP 状态、系统主页或启动项。

08 · 补充复核：许可协议与受影响的人

补充复核 · 静态代码已确认

程序内的许可协议没有提到这些行为

许可协议文本由第 17224–17245 行的函数生成，界面配有“同意／不同意”按钮（第 15588–15589 行）。如果在菜单里取消勾选“许可协议”，点击封装时会提示未接受协议并终止（第 25250–25254 行）。

协议共 8 条，内容是：封装前和部署前备份、不对系统故障负责、不保证所有硬件可用、必须完整分发、允许复制分发、可能被安全软件拦截，以及禁止破解和反编译。其中没有提到修改主页、下载或安装软件、推广或广告。

按“推广、广告、推荐、赞助、捆绑、主页、首页”等关键词搜索全部界面字符串，与推广有关的只有菜单项“VIP 免广告”（第 27533 行）和 VIP 认证对话框里的“可开启更多功能或免广告”（第 27875 行），都没有说明“广告”指什么。

这只能说明程序内没有相关告知。官网、下载页或其他渠道是否另有说明，不在本次分析范围内。

补充复核 · 解读

受影响的是部署出去的电脑

推广在部署阶段运行，软件下载安排在部署后首次登录时。使用这些电脑的人从没见过该软件的界面和协议；而是否推广，由封装者在封装那一刻的 VIP 状态决定（见 03）。

09 · 两次分析的差异

10 · 研究结论

初次分析的结论：

我们对某封装软件的 x64 样本进行了离线静态分析，发现其中存在浏览器主页修改及下载、运行外部文件的流程。在相应部署配置开启时，代码会进入这些流程；VIP 认证成功后会关闭相关标志。由于本次没有访问下载服务器或运行目标程序，尚不清楚实际会下载哪些文件、安装哪些软件。

补充复核的结论：

在这个 x64 样本中，推广流程会在用封装出来的系统部署的每台电脑上运行：修改 Edge 主页，并在部署后首次登录时下载、运行服务器下发的文件，且不做任何校验。在程序内部，关闭它的唯一途径是 VIP 认证；程序内的许可协议没有提到这些行为。实际会安装哪些软件仍无法确认，以上结论也不能外推到其他版本或在线服务的当前状态。
